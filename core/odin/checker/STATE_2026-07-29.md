## Blocker: the port no longer compiles

`odin check core/odin/checker -no-entry-point` → **25 errors**. All of them are core-library/compiler
drift, none are checker logic:

| Cause | Errors |
|---|---|
| `core:os` → os2 promotion (`e7dbabf66`): `os.read_entire_file` now returns `(data, Error)` not `(data, bool)`; `os.write_entire_file` returns `Error`; `os.processor_core_count` and `os.get_current_directory` gone | 8 |
| `path/filepath`: `join`/`abs` now return `(string, Error)`; `dir` lost its allocator parameter | 15 |
| Compiler tightening: `#partial switch &val in v` where the value isn't addressable is now an error (`exact_value.odin:303`, `:1786`) | 2 |

By file: `package_resolver` 9, `check_expr` 4, `check_decl` 4, `check_builtin` 3, `exact_value` 2,
`runtime_extractor` 1, `docs_writer` 1, `checker_lifecycle` 1.

Total migration surface is only ~40 `os.`/`filepath.` call sites. The direct replacement for
`os.processor_core_count` is `os.get_processor_core_count()` (same semantics, no allocator).

Consequence: **no test can run right now.** Last recorded run was 402 passing / 25 failing.

### How it was resolved

No second wave materialised — the 25 were the whole set. Changes, by kind:

- `filepath.join` → now returns `(string, Allocator_Error)`. Handled at all 11 sites following the
  in-tree idiom (`core/time/timezone/tz_unix.odin`): check the error, bail on failure. In
  `check_decl.odin`'s foreign-import loop the failure path reports via `error_node` and `continue`s,
  matching the existing "path cannot be empty" precedent a few lines above.
- `filepath.abs` → returns `os.Error` instead of `bool`; `filepath.dir` → **no longer takes an
  allocator and no longer allocates** (it returns a substring of its input via `split_path`). Each
  `dir` site was checked for lifetime rather than mechanically stripped:
  - `package_resolver.odin` ODIN_ROOT walk — `parent` is now a substring of `cwd`, which is allocated
    persistently, so it stays valid. Also removes a per-iteration leak.
  - `check_expr.odin` `#directory` — **fixed a latent bug.** The old code allocated the directory in
    `context.temp_allocator` and stored it as a constant `Exact_Value`, so the constant could be
    invalidated by a temp reset. The substring is owned by the token's file path and outlives it.
  - `check_decl.odin` foreign-import `base_dir`, `check_builtin.odin` `#load` — substrings of a file
    `fullpath`, valid for the scope of use.
- `os.read_entire_file` → `(data, Error)` and the allocator is now a required argument. Both call
  sites retain the data (a `#load` constant value, and the `Load_File_Cache`), so both explicitly pass
  `context.allocator`; this is what the old default did, and using temp here would be a use-after-free.
  The `#load` cache keeps its existing `os.exists` re-probe to distinguish Not_Exists from Permission —
  a precise mapping would need `io.Error.Permission_Denied` and a new import, which is a separate call.
- `os.write_entire_file` → returns `Error`; `doc_write_to_file` compares `== nil`.
- `os.get_current_directory` → `os.get_working_directory` (returns `(dir, Error)`).
- `os.processor_core_count` → `os.get_processor_core_count`.

Two of the 25 were **not** os2 but a compiler tightening: `#partial switch &val in v` in
`exact_value.odin` (`:303`, `:1786`), where `v` is a by-value `Exact_Value` and so its union payload
isn't addressable. Only the `big.Int` arm needed the pointer (`big.is_zero`, `big.int_itoa_string`),
so those arms now take a local copy. This is behaviour-preserving: any mutation those queries perform
(clearing an uninitialised `Int`) was already being discarded through the by-value parameter.

## Post-migration findings

Verifying the migration surfaced two problems. Neither is caused by the os2 changes — both are
pre-existing — but together they mean the green test suite is not evidence the checker works.

### 1. `check_package_from_path` aborts with a bad free on any real package — FIXED

> **Resolved.** 88 invalid `delete` calls removed across 7 batches, plus two one-line fixes to
> `expr_to_string` / `expr_to_string_shorthand`. The ASan probe on `core/strings` no longer aborts:
> zero AddressSanitizer reports, and the checker now runs deep enough to emit **618 real diagnostics**
> across `core/strings` and its transitive dependencies (`io`, `bytes`, `unicode/utf8`, …) before
> hitting its `max_error_count` cap and calling `os.exit(1)` — the normal cap path, not a crash.
>
> Confirmation on the exact failing path: the original ASan trace pointed at `check_type.odin:3241`,
> the `#optional_allocator_error` validation. That code now *reports* correctly instead of crashing —
> `utf8.odin(150:20) Error: A procedure type with the #optional_allocator_error expects a
> \`runtime.Allocator_Error\`, got 'enum int {None, Out_Of_Memory, …}'`.
>
> Those 618 diagnostics are the first real reading of the port's semantic accuracy and are the natural
> next thing to triage. Original analysis kept below.



Checking a real on-disk package crashes. Reduced to a three-line program calling the same entry point
the tests use, built with `-debug -sanitize:address`:

```
AddressSanitizer: attempting free on address which was not malloc()-ed
  runtime::delete_string
  checker::check_procedure_type   check_type.odin:3241
  checker::check_proc_decl        check_decl.odin:1067
  checker::check_entity_decl      check_decl.odin:634
  checker::check_single_global_entity
  checker::check_all_global_entities
  checker::check_files
  checker::check_package_from_path
0x… is located 8 bytes inside of 503-byte region
allocated by:
  checker::alloc_entity_variable  entity.odin:91
  checker::alloc_entity_param     entity.odin:121
  checker::check_get_results      check_type.odin:4310
```

`check_type.odin:3241` is `defer delete(type_str)` on a `type_to_string` result, in the
`#optional_allocator_error` validation path — code the migration never touched.

The root cause is systemic, not one bad line. `type_to_string` (`check_expr.odin:6999`) either returns
a **string literal** (`"<no type>"`, `"<invalid>"`) or a builder allocated in
**`context.temp_allocator`**. Its result must never be `delete`d, and never with the default heap
allocator. There are **~80 `delete()` calls on `type_to_string` results** across the package. This
crash is simply the first one reached; the rest are latent.

Fixing this is a mechanical sweep, but it needs a per-site check that the deleted string really is a
`type_to_string` result and not some other owned string, so it should not be done blind.

### 2. `test_check_all_core_packages` checks nothing, and cannot fail

It reports `86/86 passed, 0 check errors, 0 parse errors` in 1.3s. Both halves are wrong:

- **The paths don't resolve.** They are written as `../../../../unicode/utf16` — four levels up from
  `core/odin/checker/tests` is the repo root, so this resolves to `<repo>/unicode/utf16`. Core packages
  live under `core/`, so it needs three. Verified: `ls ../../../../unicode/utf16` from the tests
  directory fails. The vendor entries use five ups and are wrong by the same margin. No CWD makes both
  groups correct.
- **A missing package reports success anyway.** `check_package_from_path` (`package_resolver.odin:277`)
  discards the loader's `ok` with `_`. When a load fails outright, `load_result.parse_errors` is still
  `0`, the file list is empty, and `check_files` on zero files returns `true` — so the proc returns
  `ok=true, 0, 0`. Verified directly: `/nope/nothing/here` → `ok=true parse_errors=0 check_errors=0`.

So the strongest signal in the suite is vacuous, which is why 146/146 is green while a real package
crashes. Fixing the paths will turn the suite red until finding 1 is fixed — that is the correct
outcome, but it is a deliberate call to make, not a side effect to stumble into.

**Recommended order:** fix the `type_to_string` ownership bug first, then fix the test paths and the
`ok`-swallowing in `check_package_from_path`, then take a real reading against `core/`. Until then
treat "the port checks core cleanly" as unmeasured, not true.

### 3. The recurring defect: ported but never wired

Eight times now a function has been faithfully translated from C++, left in the tree, and never called.
Each one presented as a diffuse pile of nonsense diagnostics rather than as a missing feature. Known
instances: `base:runtime` never parsed, `pkg.scope` never set, `t_context` never initialised, the `ODIN_*`
build constants never registered, `check_all_scope_usages` / `check_objc_context_provider_procedures` /
`resolve_global_untyped_expressions` never invoked, and most recently `init_core_map_type`, which simply
did not exist — `t_map_info`, `t_map_cell_info` and `t_raw_map` were only ever *reset* to nil, so
`intrinsics.type_map_cell_info` handed back a **nil type** with a valid addressing mode.

When triaging a wave of unexplained diagnostics, check whether the responsible phase is *called* before
assuming it is *wrong*.

### 4. A predicate that was too strict masked a class of nil-type bugs

`is_type_typed` carried an invented `&& t != t_invalid` clause and skipped C++'s `base_type` unwrap
(`types.cpp:1419-1426`). Correcting it was mostly mechanical, but it had been returning **true for nil**,
which silently short-circuited `convert_to_typed` for every nil-typed operand. Two real defects were
hiding behind that: the `init_core_map_type` gap above, and a `check_builtin_procedure` prologue that
excluded `complex`/`real`/`imag`/`conj`/`swizzle` from the args[0] pre-check that C++ performs — leaving
`operand` holding the builtin itself, so `complex(a, b)` segfaulted.

Net effect once both were fixed: both crashes gone (reproduced on demand before, absent after), suite
unchanged at 146 tests / 7 limit-related failures in both threading modes. An apparent 94049 → 93401
drop in total sweep diagnostics was **retracted** — see finding 5, that delta is inside the measurement
noise. Follow-up work is tracked as the builtin-prologue reconciliation, and a nil-guard audit of the
`is_type_*` family.

### 5. The sweep diagnostic total cannot resolve small differences

Running the 169-package sweep twice with a **byte-identical binary** gives 93401 and 94113 — a 712-point
swing. Per package it is worse: `core/log` ranges 526–737 across runs of one build. This is not thread
scheduling (forcing `no_threaded_checker` changes nothing); the checker iterates maps keyed by `^Type`
and `^Entity`, so ASLR shifts iteration order, resolution order, and which cascades fire.

**The cause is now proven.** Odin seeds map hashing from the map's *data pointer*
(`base/runtime/dynamic_map_internal.odin:198-205`), so ASLR reorders every map iteration in the checker,
which reorders entity resolution, which changes which cascades fire. On `core/log`, four runs under
`setarch -R` give 604 every time; four runs with ASLR give 617/596/523/590. The diagnostic *sets* differ,
not merely their order — some runs report errors that others do not.

**Both halves are now fixed.** For measurement, a sweep run single-threaded under `setarch -R` is exact —
two full 169-package sweeps of one binary produce byte-identical output. And the checker itself no longer
depends on ASLR: package and file walks go through `sorted_packages` / `sorted_files`, backed by a
discovery-order registry (`Checker_Info.packages_ordered`) that mirrors C++'s `parser->packages` array.
`core/log` now returns the same count on every run with ASLR enabled.

### 6. Diagnostics depend on iteration order by ~8.7%

Determinism made it possible to compare two *valid* orders directly, and they disagree sharply: the old
arbitrary map order totals 93233 across the 169-package sweep where the new discovery order totals
101369, with **90 of 169 packages** differing. The categories that move are the used-before-resolved
symptoms — on `core/log`, "Cannot determine type for implicit selector expression" goes 45 → 190 while
"Enumeration value must be a constant" goes 150 → 94.

A correct checker is order-independent: referencing an unresolved entity must force its resolution. The
port has that machinery but not on every path. Neither total is known to be correct, and no improvement
should be inferred from either. This is probably the largest remaining source of false diagnostics, and
it is tracked as open structural work.

### 7. Every u64-range integer literal was stored as a negative i64

`parse_exact_value_from_token` tried `strconv.parse_i64_maybe_prefixed` first and fell back to the
unsigned parse only if that call *failed*. It never fails — for values above `max(i64)` it returns
`ok=true` with the value silently wrapped negative, so `0xaaefdd6dcd770416` became
`-6129437104159652842`. The unsigned branch was therefore dead code, and
`check_representable_as_constant` then quite correctly refused to convert a negative constant to `u64`.
`core/hash/crc.odin` alone produced 388 of these.

Fixed by parsing unsigned first — an integer literal token never carries a sign, since `-x` is a unary
operator applied to the literal — and choosing the signed representation only when the value fits.
`core/hash` went 878 → 708 and the deterministic 169-package sweep 101369 → 98553.

Two related gaps remain: literals wider than `u64` return nil where C++ carries them in a BigInt, and
the imaginary-literal mantissa still uses the signed parse (reachable only for u64-range imaginary
literals, since a float parse is attempted first).
